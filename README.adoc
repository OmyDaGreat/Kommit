A simple command-line tool written in Kotlin that helps generate conventional commit messages based on a YAML configuration file. Using standardized configuration formats across your team, Kommit ensures consistency and clarity, making it easier to understand the history of your project and collaborate effectively.

== Features

* Follows the link:https://www.conventionalcommits.org/[Conventional Commits] specification
* Customizable commit types, scopes, and other options through a YAML configuration file
* Interactive CLI prompts to guide you through creating well-formatted commits
* Support for multi-line commit bodies, breaking changes, and issue references
* GPG tooling for Git commit signing and testing

== Quick Start

[source,sh]
----
# Walk through creating a configuration file (make sure to commit this file for team use)
kommit create

# Generate a commit message
kommit
----
That's it! It's really that simple!

== Command Reference

Kommit provides subcommands for generating commits, managing configuration, and
working with GPG signing:

=== Commit Management
* `kommit`/`kommit commit`: Generate a conventional commit message using the config file
* `kommit create`: Interactively create a `.kommit.yaml`, choosing commit types, scopes (suggested from your git history), and options. Use `--defaults` to skip the prompts and `--config PATH` to write elsewhere

=== GPG Management
* `kommit gpg`: Parent command for GPG-related operations
** `kommit gpg test`: Test if the GPG agent is working by signing a test message
** `kommit gpg reset`: Reset the GPG agent to fix signing issues

TIP: Run `kommit --help` to see all available commands and options.

== Configuration

=== Configuration File Location

By default, Kommit looks for a `.kommit.yaml` file in the current directory. You can specify a different configuration file using the `--config` option:

[source,sh]
----
kommit --config path/to/config.yaml
----

=== Configuration File Format

The configuration file uses a YAML-inspired format:

[source,yaml]
----
# Commit Types
types:
  - feat: A new feature
  - fix: A bug fix
  - docs: Documentation only changes
  - style: Changes that do not affect the meaning of the code
  - refactor: A code change that neither fixes a bug nor adds a feature
  - perf: A code change that improves performance
  - test: Adding missing tests or correcting existing tests
  - build: Changes that affect the build system or external dependencies
  - ci: Changes to CI configuration files and scripts
  - chore: Other changes that don't modify src or test files

# Available Scopes
scopes:
  all:
    - core
    - ui
    - api
    - auth
    - db
  chore:
    - github
    - deps
    - release

# Configuration Options
options:
  stageMode: none
  autoPush: true
  allowBreakingChanges: true
  allowIssues: true
  allowBody: true
----

=== Configuration Options Explained

[cols="1,3"]
|===
|Option |Description

|`types`
|List of commit types with their descriptions. Each type follows the format `type: Description`.

|`scopes`
|List of available scopes. You can define scopes for all commit types under the `all` key, or specific scopes for particular commit types.

|`options.allowBody`
|Whether to prompt for a multi-line body (true/false). When enabled, Kommit will prompt for a longer description, which is entered one line at a time and finished by pressing Enter on an empty line (leave it blank to skip). The body is placed after the header, separated by a blank line. By default, Kommit will prompt for a body.

|`options.allowBreakingChanges`
|Whether to prompt for breaking changes (true/false). When enabled, Kommit will ask whether the commit is a breaking change; if it is, a `!` is added after the type/scope in the header, and an optional description is added to the footer after `changesPrefix`. By default, Kommit will prompt for breaking changes.

|`options.allowCustomScopes`
|Whether to allow custom scopes (true/false). When enabled, users can enter scopes not defined in the configuration. By default, users can enter custom scopes not defined in the configuration.

|`options.allowEmptyScopes`
|Whether to allow empty scopes (true/false). When enabled, users can create commits without a scope. By default, commits can be created without specifying a scope.

|`options.allowIssues`
|Whether to prompt for issue references (true/false). When enabled, Kommit will prompt for issue numbers, entered comma-separated (e.g. `123,456`) or left blank to skip. The issues are added to the commit footer after `issuePrefix`. By default, Kommit will prompt for issue references.

|`options.autoPush`
|Whether to automatically push changes after a successful commit (true/false). When enabled, Kommit will push your changes to the remote repository immediately after committing. By default, changes are not pushed automatically.

|`options.changesPrefix`
|The prefix used for breaking changes in the footer. By default, breaking changes are prefixed with 'BREAKING CHANGE:' in the commit footer, as required by the Conventional Commits specification. Changing it may prevent tools such as semantic-release from detecting breaking changes.

|`options.issuePrefix`
|The prefix used for issue references in the footer. By default, issue references are prefixed with 'ISSUES CLOSED:' in the commit footer.

|`options.stageMode`
|How Kommit stages changes before committing (none/review/auto). `none`: Kommit only commits what is already staged and stops with a reminder if nothing is. `review`: right before committing, Kommit lists every changed file (staged, unstaged and untracked) and lets you pick which ones to stage and commit; unselected files are unstaged. `auto`: if nothing is staged, Kommit stages all changes automatically. Defaults to `none`.
|===

== Common Issues

=== Git Not Found

If you see an error like "Git command not found", ensure that Git is installed and available in your system PATH.

=== Kommit Not Seeing Staged Changes

If you're running Linux, make sure you have `less` installed, as `git` uses that to display staged changes.

=== Configuration File Not Found

If Kommit can't find your configuration file, make sure it exists at the expected location (the project root), specify the path using the `--config` option, or create it with `kommit create`.
